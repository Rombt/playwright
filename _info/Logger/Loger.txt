Logging Architecture
    1. Назначение
        Система логирования предназначена для:
            Отслеживания выполнения задач (Job / Scenario)
            Диагностики ошибок
            Анализа параллельных процессов
            Исторического хранения событий
            Контролируемого роста системы без архитектурных изменений
            Логирование является инфраструктурной ответственностью и не относится к бизнес-логике.
    2. Архитектурные принципы
        2.1 Clean Layers
            Logger является инфраструктурным сервисом.
                При этом
                    все зависимости направлены вниз.
                    оперирует только структурированными лог-записями.
                    ни один слой системы не знает о реализации логгера.
            Logger:
                Не относится к Scenario
                Не относится к Source
                Не относится к Browser
                Не относится к Storage
                Не импортирует Playwright
                Не знает о Page
                Не знает о BrowserContext
                Не знает о Response
    3. Архитектурная модель
        3.1 Singleton
            В системе существует один корневой экземпляр Logger.
            Он создаётся при инициализации приложения.
            Назначение root logger:
                Хранить конфигурацию
                Хранить уровень логирования
                Управлять transports
                Создавать scoped logger
                Root logger не содержит бизнес-данных.
        3.2 Stateful (контролируемое состояние)
            Это достигается тем что
            Logger хранит только инфраструктурное состояние:
                Допустимо:
                    currentLogLevel
                    список transports
                    форматтер
                    глобальные поля (например appName)
                Недопустимо:
                    jobId
                    sku
                    retryCount
                    browser instance
                    page
                    domain объекты
        3.3 Immutable Scoped Logger
            Для каждой задачи создаётся
            scoped logger:
                logger.withContext(contextId)
                Scoped logger:
                    Ссылается на root logger
                    Хранит собственный contextId
                    Не позволяет изменить context после создания
                Контекст неизменяем (immutable).
                Это гарантирует:
                    Изоляцию параллельных задач
                    Отсутствие “перетекания” логов
                    Предсказуемость поведения
    4. ContextId
        4.1 Назначение
            contextId — уникальный идентификатор Job / Scenario.
            Он обеспечивает:
                Изоляцию параллельных процессов
                Возможность фильтрации логов
                Анализ конкретной задачи
        4.2 Использование
            contextId добавляется автоматически каждым scoped logger.
            Разработчик не обязан передавать его вручную в каждый вызов.
    5. Structured Logging
        5.1 Принцип
            Каждая запись формируется как структурированный объект:
                timestamp
                level
                message
                contextId
                meta (произвольные данные)
            5.2 Причины выбора
                Structured logging:
                    Упрощает фильтрацию
                    Делает логи машиночитаемыми
                    Предотвращает хаотичный текстовый вывод
    6. Уровни логирования
        Logger поддерживает уровни:
            error
            warn
            info
            debug
        Root logger хранит текущий уровень.
        Фильтрация выполняется до передачи записи в transport.
    7. Разделение ответственности
        7.1 Logger отвечает за:
            Формирование log entry
            Добавление timestamp
            Добавление contextId
            Проверку уровня
            Передачу записи в transports
        7.2 Transport отвечает за:
            Запись в console
            Запись в файл
            Любую другую форму вывода
        Logger не знает:
            Как устроена файловая система
            В каком формате пишется файл
            Как устроена консоль
            Transport изолирован.
    8. Поддерживаемые transports (на старте)
        Минимальный набор:
            Console transport
            File transport
        Дополнительные transports могут быть добавлены без изменения API Logger.
    9. Интеграция в слои системы
            Scenario создаёт scoped logger
            Scoped logger передаётся вниз
            Source / Browser / Storage используют его
    10. Принципы расширяемости
        Архитектура позволяет в будущем:
            Добавить новые transports
            Переключить формат вывода
            Добавить асинхронную запись
            Подключить удалённый лог-сервер
            Включить трассировку
    11. Ограничения
        Logger:
            Не должен хранить доменные данные
            Не должен принимать бизнес-решения
            Не должен выполнять retry-логику
            Не должен зависеть от внешних библиотек бизнес-уровня
            Он остаётся инфраструктурным сервисом.
    12. Итоговая модель
        Система логирования проекта основана на:
            Singleton root logger
            Immutable scoped logger
            Structured logging
            Разделении logger / transport
            Контракте ILogger
            Поддержке contextId
            Контролируемом stateful состоянии
        Это обеспечивает:
            Удобство использования
            Чистоту архитектуры
            Изоляцию параллельных задач
            Готовность к умеренному росту
            Отсутствие избыточной сложности на старте
