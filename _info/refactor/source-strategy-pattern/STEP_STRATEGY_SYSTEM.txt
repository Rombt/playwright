STEP STRATEGY SYSTEM
(Strategy Layer inside Step-based Flow Architecture)

ОБЩЕЕ ОПРЕДЕЛЕНИЕ

Strategy — это механизм выбора конкретной реализации поведения внутри одного шага (Step).

В рамках архитектуры:
    Step отвечает за ЧТО делать
    Strategy отвечает за КАК это делать

Один Step может иметь несколько стратегий,
каждая из которых реализует альтернативный способ выполнения одной и той же задачи.

Пример:
    Step: CheckSearchResultsStep

    Возможные стратегии:
        - Поиск через link + empty блок
        - Поиск через список похожих товаров
        - Поиск через текст SKU
        - fallback стратегия

Все стратегии внутри одного Step:
    выполняют одну и ту же логическую задачу
    возвращают одинаковый результат (единый контракт)

РОЛЬ STRATEGY В АРХИТЕКТУРЕ

Strategy не управляет flow.

Strategy:
    не знает о следующих шагах
    не вызывает другие шаги
    не принимает решений о переходах

Strategy:
    получает данные
    выполняет операцию
    возвращает результат

Управление остаётся в Step.

КОНТРАКТ СТРАТЕГИИ

Базовый интерфейс:

    interface IStrategy<TParams = unknown, TResult = unknown> {
        name: string;

        canHandle(ctx: IExecutionContext): Promise<boolean>;

        score(ctx: IExecutionContext): Promise<number>;

        execute(ctx: IExecutionContext, params: TParams): Promise<TResult>;
    }

Описание:

    name
        уникальное имя стратегии
        используется для логирования и отладки

    canHandle(ctx)
        проверяет применимость стратегии к текущему DOM/состоянию
        возвращает true/false

    score(ctx)
        оценивает "качество" стратегии
        используется при выборе между несколькими подходящими стратегиями

    execute(ctx, params)
        выполняет основную работу
        возвращает результат, строго соответствующий контракту Step

ПАРАМЕТРЫ (TParams)

Strategy получает параметры явно через execute:

    execute(ctx, params)

Параметры передаются из Step.

Важно:
    Strategy НЕ должна извлекать параметры из ctx.state или ctx.input,
    если они уже переданы через params.

Это обеспечивает:
    прозрачность
    предсказуемость
    контроль контракта

РЕЗУЛЬТАТ (TResult)

TResult определяется на уровне Step, а не глобально.

Пример:

    type SearchResult = {
        productUrl: string;
    };

    strategies: IStrategy<CheckSearchResultsParams, SearchResult>[]

Все стратегии внутри одного Step обязаны:
    возвращать один и тот же TResult

Это даёт:
    строгую типизацию
    отсутствие runtime-ошибок
    предсказуемость поведения

СВЯЗЬ STEP И STRATEGY

Поток выполнения:

    Step получает params
        ↓
    Step выбирает Strategy через Resolver
        ↓
    Strategy.execute(ctx, params)
        ↓
    Step получает TResult
        ↓
    Step записывает результат в ctx.state

Формула:

    params → Strategy → result → ctx.state

STRATEGY RESOLVER

Resolver отвечает за выбор стратегии.

Интерфейс:

    interface IStrategyResolver {
        resolve<TParams, TResult>(
            ctx: IExecutionContext,
            strategies: IStrategy<TParams, TResult>[],
            stepName: string,
        ): Promise<IStrategy<TParams, TResult>>;
    }

Алгоритм:

    1. Фильтрация:
        стратегии, где canHandle(ctx) === true

    2. Ранжирование:
        вычисление score(ctx)

    3. Сортировка:
        по убыванию score

    4. Выбор:
        стратегия с максимальным score

    5. Ошибка:
        если ни одна стратегия не подошла

EXPLAINABILITY (ПРОЗРАЧНОСТЬ)

Все решения Resolver логируются в ctx.debug:

    ctx.debug.strategies.push({
        step: stepName,
        strategy: strategy.name,
        score: value,
        selected: boolean
    });

Это обеспечивает:
    понимание, почему выбрана стратегия
    удобную отладку
    возможность анализа поведения системы

РАБОТА С CONTEXT

ExecutionContext остаётся центральным элементом.

Strategy:
    читает данные из ctx
    использует ctx.page (или actions)
    не управляет структурой ctx

Step:
    записывает результат в ctx.state

Для предотвращения "засорения" состояния рекомендуется:

    state: {
        productUrl?: string;
        images?: string[];
        description?: string;
        html?: string;

        strategy?: Record<string, unknown>;

        [key: string]: unknown;
    }

Поле strategy используется для временных данных стратегий.

ПРИНЦИПЫ ПРОЕКТИРОВАНИЯ

1. Один Step — один контракт результата
    Все стратегии возвращают одинаковый TResult

2. Strategy не управляет flow
    Только выполнение, без переходов

3. Context — единая точка данных
    Не вводить дополнительные контейнеры без необходимости

4. Минимум абстракций
    Не создавать новые интерфейсы без реальной выгоды

5. Явные параметры
    params передаются из Step, а не извлекаются хаотично

6. Explainability обязателен
    Любой выбор стратегии должен быть логируемым

КОГДА ДОБАВЛЯТЬ НОВУЮ STRATEGY

Новая стратегия нужна, если:

    - сайт имеет другой DOM
    - нет стандартных маркеров (empty, link и т.п.)
    - требуется другая логика извлечения данных
    - текущие стратегии становятся перегруженными условиями

Не нужно создавать стратегию, если:

    - отличие незначительное
    - можно параметризовать существующую

ЧТО НЕ НУЖНО ДЕЛАТЬ

- Не выносить параметры в отдельные контексты (IStrategyContext)
- Не дублировать данные вне ExecutionContext
- Не возвращать debug из resolver (использовать ctx.debug)
- Не создавать отдельный интерфейс под каждую стратегию без необходимости
- Не использовать unknown как итоговый контракт Step

ИТОГ

Strategy Layer:
    добавляет гибкость без усложнения flow
    позволяет адаптироваться к различным сайтам
    сохраняет прозрачность выполнения

Архитектурный баланс достигается через:
    единый ExecutionContext
    строгие контракты на уровне Step
    минимально необходимую типизацию
