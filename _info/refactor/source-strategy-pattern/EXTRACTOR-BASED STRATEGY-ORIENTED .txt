EXTRACTOR-BASED (STRATEGY-ORIENTED) SOURCE ARCHITECTURE

Это соответствует паттерну Strategy.

Данная архитектура строится вокруг принципа: 
    источник (Source) — это композиция переиспользуемых стратегий извлечения данных (extractors), 
    которые инкапсулируют логику получения конкретных типов данных со страницы.

Scraping рассматривается как процесс:
    перехода на страницу (resolver)
    извлечения данных (extractors)
    сборки результата (builder)

Основной акцент делается на повторном использовании логики извлечения и декларативной конфигурации источников.

Ключевые элементы архитектуры

    Source (оркестратор) - это класс, реализующий общий контракт (ISource) и конфигурирующий:
        стратегию навигации (resolver)
        набор extractors
        правила сборки результата
    Он:
        определяет, подходит ли для задачи (supports)
        управляет жизненным циклом выполнения (execute)
        координирует resolver и extractors
        возвращает результат

Сигнатура (упрощённо):

interface ISource<TTask> {
    supports(task: TTask): boolean;

    execute(
        targetUrl: string,
        page: Page,
        options?: {},
        debugMeta?: Record<string, string>,
        sku?: string,
        ): Promise<IWorkerResult>;
    }

Source в этой модели остаётся относительно “тонким” и делегирует основную работу стратегиям.

    BasePageSource (шаблон выполнения) - задаёт общий pipeline выполнения:
        навигация (resolver)
        извлечение данных (extract)
        сборка результата (buildResult)

Пример последовательности:
    resolve(page, url) → extract(page) → buildResult(data)

Это реализация паттерна Template Method.

BasePageSource:
    фиксирует структуру выполнения
    предоставляет расширяемые точки (extractors)
    инкапсулирует общую логику

Resolver (стратегия навигации)
    Resolver отвечает за переход на нужную страницу и её базовую стабилизацию 
        при этом
            изолирует навигацию
            переиспользуется между Source
            не знает о конкретных данных
    Интерфейс:
        interface IPageResolver {
            resolve(page: Page, targetUrl: string, debugMeta?: Record<string, string>): Promise<void>;
        }
    Пример реализации:
        прямой переход (DirectPageResolver)
        возможные альтернативы: через редиректы, авторизацию, промежуточные страницы

Extractor (стратегия извлечения)
    Extractor — это стратегия, отвечающая за извлечение конкретного типа данных.
        при этом:
            получает page
            извлекает данные
            возвращает результат
            не управляет сценарием
    Интерфейсы:
        interface IExtractor<T> {
            extract(page: Page, debugMeta?: Record<string, string>): Promise<T>;
        }

    Специализации:
        interface IImageExtractor extends IExtractor<string[]> {}
        interface IDescriptionExtractor extends IExtractor<string | null> {}

    Классификация extractors
        По типу данных:
            ImageExtractor (изображения)
            DescriptionExtractor (описание)
            возможные расширения: PriceExtractor, AttributesExtractor
        По сложности:
            простые (один selector)
            составные (несколько selector, фильтрация)
            интерактивные (включают клики, ожидания)

Конфигурация Source
    Source собирается путём задания стратегий:
        protected resolver: IPageResolver;
        protected imageExtractor?: IImageExtractor;
        protected descriptionExtractor?: IDescriptionExtractor;

    Это декларативный стиль:
        выбираются нужные компоненты
        поведение определяется их комбинацией
        Процесс выполнения (Pipeline)
    
    Выполнение состоит из фиксированных этапов:
        Resolver
            переход на страницу
            базовая стабилизация DOM
        Extraction
            вызов imageExtractor
            вызов descriptionExtractor
        Result Builder
            преобразование данных в нужный формат
            добавление metadata (например, sku)

        Пример:
            await resolver.resolve(...)
            const data = await extract(...)
            return buildResult(data)

    Метод extract
        выступает как координатор, а не как исполнитель логики.
        агрегирует работу extractors:
            проверяет наличие extractor
            вызывает extract
            собирает результат
        Возвращает:
            {
                images?: string[]
                description?: string | null
            }

    Метод Result Builder
        отделяет извлечение от представления
        преобразует “сырые” данные extractors в финальную модель.
        адаптирует данные под систему

        Пример:
            преобразование массива URL в IDataImag
            добавление sku
            нормализация структуры

    Worker слой
        Worker — это дополнительный уровень, который:
            получает product
            подготавливает входные данные
            вызывает execute
            возвращает массив результатов
        при этом:
            связывает Source с pipeline задач
            обеспечивает совместимость с внешней системой
            Обработка ошибок

    Ошибки:
        могут возникать в resolver
        могут возникать в extractors
        собираются в массив
        не обязательно прерывают весь pipeline
        возможна частичная успешность

Переиспользование достигается через:
    Extractors
        один extractor может использоваться в разных Source
    Resolvers
        один resolver может применяться для разных сайтов
    BasePageSource
        общий pipeline для всех Source

Отличительные свойства архитектуры
    Декларативность
        Source описывает “что использовать”, а не “как делать”.
    Переиспользуемость
        Extractors и resolvers могут комбинироваться.
    Разделение ответственности
        resolver — навигация
        extractor — извлечение
        builder — сборка результата
    Централизация pipeline
        BasePageSource управляет порядком выполнения.
    Ограничения архитектуры
        Фиксированный pipeline
        Сложно выразить сценарии с ветвлениями и несколькими переходами.
    Ограниченный контекст
        Extractors получают только page и не имеют доступа к полному состоянию.
    Сложность расширения
        При нестандартной логике приходится переопределять execute.
    Скрытая логика
        Часть поведения уходит внутрь extractors и становится менее явной.

Подходит для:
    простых страниц (один URL → данные)
    стабильных DOM
    типовых задач извлечения
    случаев без сложной навигации

Итог
    Extractor-based архитектура 
        рассматривает scraping как комбинацию стратегий извлечения данных, объединённых общим pipeline.
        позволяет:
            переиспользовать логику извлечения
            декларативно конфигурировать источники
            стандартизировать процесс получения данных

Главный принцип:
    данные извлекаются через независимые стратегии, 
    а Source выступает как координатор этих стратегий в рамках фиксированного процесса выполнения.
