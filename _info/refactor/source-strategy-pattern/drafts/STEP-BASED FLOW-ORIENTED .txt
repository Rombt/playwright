STEP-BASED (FLOW-ORIENTED) SOURCE ARCHITECTURE

Данная архитектура строится вокруг принципа: 
    источник (Source) — это не набор отдельных операций по извлечению данных, 
    а сценарий (flow), описывающий последовательность действий, необходимых для получения результата.

Scraping рассматривается как процесс с управлением состоянием и поведением, 
    включающий переходы между страницами, ожидания, проверки, ветвления и только в конце — извлечение данных. 
    Поэтому архитектура должна явно отражать этот процесс.

Основной объект — это сценарий, состоящий из шагов. 
    Каждый шаг — это атомарная операция, а весь Source — это композиция таких шагов.

Ключевые элементы архитектуры
    Source (сценарий) - явно описывает, что происходит шаг за шагом.
        это реализация конкретного сценария работы с сайтом который:
            определяет, подходит ли для задачи (supports)
            описывает последовательность шагов (flow)
            управляет выполнением шагов
            возвращает результат
    Сигнатура:
        interface ISource<TTask, TResult> {
            supports(task: TTask): boolean;
            run(ctx: SourceContext<TTask>): Promise<SourceResult<TResult>>;
        }

SourceContext (контекст выполнения)
    Контекст — это единая точка передачи всех зависимостей и входных данных.
    Он включает:
        page (Playwright Page)
        request (для HTTP, если нужен)
        task (входная задача)
        product (если применимо)
        limiter (rate limiter)
        logger
        debugMeta

        Пример:
            interface SourceContext<TTask> {
                page: Page;
                request?: APIRequestContext;

                task: TTask;
                product?: IProduct;

                limiter: RateLimiter;
                logger: ILogger;

                debugMeta?: Record<string, string>;
            }

Контекст передаётся во все шаги и не мутируется (за исключением контролируемых случаев).

FlowState (состояние сценария)
    FlowState — это объект, в котором накапливаются промежуточные данные сценария.
        создаётся внутри Source
        передаётся во все шаги
        используется для передачи данных между шагами

    Пример:
        type FlowState = {
            sku?: string;
            searchUrl?: string;
            productUrl?: string;

            images?: string[];
            description?: string;

            flags?: Record<string, boolean>;
        };

    FlowState заменяет передачу параметров между функциями и делает состояние сценария явным.

Step (шаг сценария)
    Step — это атомарная операция, выполняемая в рамках сценария.
    Сигнатура:
        type Step<TTask = any, TState = any> = (
            ctx: SourceContext<TTask>,
            state: TState
        ) => Promise<void>;
    Каждый шаг:
        выполняет одну логическую операцию
        может читать и изменять state
        может использовать ctx
        может выбрасывать ошибки
    Классификация шагов
        по назначению:
            Навигационные:
                открыть страницу
                перейти по ссылке
                изменить URL
            Синхронизационные:
                ожидание появления элемента
                ожидание состояния страницы
                паузы
            Интерактивные:
                клик
                ввод текста
                скролл
                переключение вкладок
            Валидационные:
                проверка наличия элемента
                проверка SKU
                проверка состояния страницы
            Экстракционные:
                извлечение изображений
                извлечение описания
                сбор данных из DOM
            Управляющие:
                условные переходы
                fallback логика
                обработка альтернативных сценариев
                Выполнение сценария (Flow Execution)

    Source описывает сценарий как массив шагов:
        const steps: Step[] = [
            openSearchPage,
            findProductLink,
            openProductPage,
            validateSku,
            extractImages,
            extractDescription,
        ];

Выполнение:
    for (const step of steps) {
        await step(ctx, state);
    }

    Это даёт:
        явный порядок выполнения
        предсказуемость
        возможность динамически изменять сценарий
        Обработка ошибок
Ошибки обрабатываются на уровне Source.
    шаги могут выбрасывать ошибки
    Source перехватывает ошибки
    ошибки сохраняются в SourceResult

    Пример:
        try {
            for (const step of steps) {
            await step(ctx, state);
        }
        } catch (error) {
            errors.push({ error });
        }

    Важно:
        шаг не обязан обрабатывать все ошибки
        критические ошибки прерывают сценарий
        некритические можно обрабатывать внутри шага

Result Builder
    После выполнения сценария происходит сбор результата из state.

    Пример:
        function buildResult(state: FlowState): ProductData {
            return {
                images: state.images,
                html: state.description,
            };
        }

Source возвращает:
    {
        data: buildResult(state),
        errors
    }

Утилиты
    Утилиты — это вспомогательные функции, не являющиеся частью архитектуры.

    Они:
        не управляют выполнением сценария
        не задают структуру системы
        используются внутри шагов

    Примеры:
        extractImages(page)
        waitForVisible(locator)
        normalizeSku(sku)

    Утилиты переиспользуются, но не навязывают архитектуру.

    Повторное использование
        Переиспользование достигается на двух уровнях:
            Шаги
            openPage
            waitFor
            click
            extractImages
            Утилиты
            функции для работы с DOM
            нормализация данных
            парсинг

Source создаётся путём композиции шагов, а не наследования.

Итог
    Step-based архитектура рассматривает scraping как управляемый сценарий, а не как набор операций извлечения данных.

Она позволяет:
    явно контролировать поведение
    гибко строить сценарии
    избегать избыточных абстракций
    масштабировать систему без усложнения интерфейсов

Главный принцип:
    поведение (flow) важнее извлечения (extraction), и архитектура должна отражать именно поведение.
