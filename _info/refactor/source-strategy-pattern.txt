Refactor: переход на Strategy Pattern в Source слое

Краткое описание
В рамках рефакторинга вводится архитектура на базе Strategy Pattern для слоя Source (Playwright). Цель — устранить дублирование кода между источниками (сайтами) и выделить переиспользуемые стратегии для навигации, извлечения изображений и описаний.

Принцип работы
Каждый источник (сайт) больше не реализует всю логику самостоятельно. Вместо этого он:

* наследуется от базового абстрактного класса BasePageSource
* конфигурируется набором стратегий (resolver, extractor и т.д.)
* передаёт параметры (например, CSS-селекторы)

Стратегии инкапсулируют поведение и могут переиспользоваться между разными сайтами.

Историческая мотивация
Изначально логика парсинга писалась отдельно для каждого сайта, что приводило к:

* дублированию кода
* сложностям поддержки
* невозможности масштабирования

Переход к параметризации (через селекторы) частично решил проблему, но не учитывал различия в поведении сайтов. Strategy Pattern выбран как следующий шаг эволюции, позволяющий разделить:

* “что делаем” (стратегия)
* “с чем работаем” (селекторы/параметры)

Архитектура

1. Базовый класс источника

BasePageSource задаёт общий pipeline:

* получение страницы (resolver)
* извлечение данных (extractors)
* возврат результата

Конкретный источник лишь конфигурирует стратегии:

class PumaSource extends BasePageSource<ICollectProductPhotosTask> {
protected resolver = new DirectPageResolver();

protected imageExtractor = new SwatchGalleryExtractor();

protected descriptionExtractor = new SimpleDescriptionExtractor(
'[data-pdp-description-container] > div'
);
}

2. Стратегии (ключевые абстракции)

Resolver (навигация):

* DirectPageResolver — переход по прямой ссылке
* SearchResolver — поиск товара
* (в будущем) ApiResolver / SPAResolver

ImageExtractor:

* SwatchGalleryExtractor — галерея через свотчи
* (в будущем) CarouselExtractor, StaticImageExtractor

DescriptionExtractor:

* SimpleDescriptionExtractor — простой DOM-блок
* (в будущем) ExpandableDescriptionExtractor, ApiDescriptionExtractor

Ключевой принцип:
Стратегия = логика + параметры

Когда достаточно только селекторов
Можно переиспользовать стратегию без изменений, если:

* структура DOM отличается, но поведение одинаковое
* данные уже присутствуют в DOM
* не требуется дополнительных действий (клики, ожидания, прокрутка)

Пример:
SimpleDescriptionExtractor(selector)

Когда требуется новая стратегия
Нужно создавать новую стратегию, если отличается поведение:

Примеры:

* описание скрыто за кнопкой → ExpandableDescriptionExtractor
* данные загружаются через API → ApiDescriptionExtractor
* изображения меняются при клике → SwatchGalleryExtractor
* требуется прокрутка или lazy-load → отдельный extractor

Главное правило:
Повторное использование возможно при совпадении поведения, а не только структуры.

Преимущества новой архитектуры

* устранение дублирования
* явное разделение ответственности
* упрощение добавления новых источников
* масштабируемость
* тестируемость отдельных стратегий

Ограничения и осознанные решения

* не используется декларативный подход (JSON-конфиги), т.к.:

  * он плохо покрывает сложное поведение
  * усложняет отладку
  * приводит к “магии” вместо явной логики

* предпочтение отдаётся явным стратегиям (классам), а не универсальным решениям с множеством условий

Правила разработки новых источников

1. Не писать новую логику сразу
   Сначала проверить:

* можно ли использовать существующий resolver
* можно ли использовать существующие extractors

2. Использовать композицию
   Источник должен собираться из готовых стратегий

3. Создавать новую стратегию только если:

* поведение сайта не покрывается текущими стратегиями
* попытка “впихнуть” логику в существующую стратегию приведёт к усложнению

4. Избегать универсальных классов с if/else
   Это приводит к деградации архитектуры

Дальнейшее развитие

* расширение набора стратегий
* покрытие edge-case сайтов (например, Rozetka) отдельными реализациями
* возможный переход к частично декларативной конфигурации (на уровне параметров, но не логики)

Итог
Source слой превращается из набора разрозненных реализаций в композиционную систему, где новые источники создаются за счёт конфигурации стратегий, а не копирования кода.
